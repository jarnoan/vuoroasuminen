## Objective

Establish the data + server foundation for clearing schedule cells. Make `schedule_entries.parent_id` nullable, widen the `ScheduleCell.parentId` TypeScript type to allow `null`, add the `clearCell` and `clearRange` Server Actions (both auth-guarded), and ensure the existing GCal publish sync naturally cleans up calendar events for cleared entries.

This plan ships zero UI. It only creates the contract that the Wave 2 UI plans (07-02, 07-03) will consume. Without this plan, the UI cannot mutate any data and TypeScript will not compile against `parentId: null`.

> **Authoring task count note:** This plan contains 5 `<task>` entries, but Task 2 is a non-authoring CLI command (`drizzle-kit push` migration step). The effective authoring task count is **4** (Tasks 1, 3, 4, 5). Total modified LOC across all authored files is <100. The plan is sized within budget; Task 2 is split out only because the migration must complete before Tasks 3–5 can compile and the database state has to advance independently of the schema source change.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → Server Action | Authenticated parent's browser invokes `clearCell` / `clearRange` over Next.js Server Actions; payload is fully untrusted. |
| Server Action → DB | Drizzle parameterized queries cross into PostgreSQL; SQL injection prevented by Drizzle bindings. |
| Server (publish) → Google Calendar API | OAuth-bearing requests delete events from each parent's calendar; failure here must not roll back DB state (per existing D-05 in Phase 4). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-01 | Spoofing | `clearCell`, `clearRange` Server Actions | mitigate | Both call `requireAuthorizedParent()` (existing helper, lines 16-23 of `src/actions/schedule.ts`) at the very top before any DB mutation; throws `Not authenticated` / `Forbidden` if session email is missing or not in `config.parents`. |
| T-07-02 | Tampering | `clearCell(entryId)` payload | mitigate | Only the `entryId` text column is matched; Drizzle parameterizes via `eq(scheduleEntries.id, entryId)` — no string interpolation. The action ignores all other fields. Empty-string entryId rejected with `success: false, error: "Missing entryId"`. |
| T-07-03 | Tampering | `clearRange({startDate, endDate})` payload | mitigate | Inputs validated with `parseISO` + `isValid` (reject `Virheellinen päivämäärä`); `differenceInCalendarDays` rejects negative deltas (`Päättymispäivän on oltava alkamispäivän jälkeen`); range capped at 730 days (`Aikaväli on liian pitkä (max 2 vuotta)`) to prevent unbounded UPDATE. Drizzle `gte`/`lte` parameterize the SQL. |
| T-07-04 | Repudiation | DB mutations | accept | No audit log in v1.x (AUDT-01/02 deferred per REQUIREMENTS.md §Future). Acceptable: only two authorized parents ever execute these actions. |
| T-07-05 | Information Disclosure | Error responses | mitigate | Server Actions return generic Finnish error strings; never leak DB error messages or stack traces to the client. `try/catch` in callers maps unknown failures to a generic toast in 07-02/07-03. |
| T-07-06 | Denial of Service | `clearRange` UPDATE scope | mitigate | 730-day cap; `schedule_entries (childId, day)` already indexed; the UPDATE matches on `day` column (date-typed, indexed implicitly via the unique index) so worst case is ~730 × N children rows. Bounded and acceptable. |
| T-07-07 | Elevation of Privilege | Cross-account clearing | mitigate | App is single-tenant (two parents share one schedule). `requireAuthorizedParent()` only allows emails listed in `config.parents`. Any other authenticated Google user gets `Forbidden`. |
| T-07-08 | Information Disclosure (GCal) | Stale GCal events for cleared entries | mitigate | `parentId: null` entries naturally fail the `entry.parentId !== parent.id` orphan check (`null !== "father"` / `null !== "mother"` are both true), so existing orphan-cleanup deletes their Google Calendar events on next publish. No new code path required beyond the type widening. |
</threat_model>

Append exactly:

```typescript

export async function clearCell(entryId: string): Promise<
  | { success: true }
  | { success: false; error: string }
> {
  await requireAuthorizedParent()

  if (!entryId) return { success: false, error: "Missing entryId" }

  await db.update(scheduleEntries)
    .set({ parentId: null, status: "draft" })
    .where(eq(scheduleEntries.id, entryId))

  return { success: true }
}

export async function clearRange(input: {
  startDate: string  // ISO YYYY-MM-DD (inclusive)
  endDate: string    // ISO YYYY-MM-DD (inclusive)
}): Promise<
  | { success: true; clearedCount: number }
  | { success: false; error: string }
> {
  await requireAuthorizedParent()

  const start = parseISO(input.startDate)
  const end = parseISO(input.endDate)

  if (!isValid(start) || !isValid(end)) {
    return { success: false, error: "Virheellinen päivämäärä" }
  }

  const daysDelta = differenceInCalendarDays(end, start)
  if (daysDelta < 0) {
    return { success: false, error: "Päättymispäivän on oltava alkamispäivän jälkeen" }
  }
  if (daysDelta > 730) {
    return { success: false, error: "Aikaväli on liian pitkä (max 2 vuotta)" }
  }

  const result = await db.update(scheduleEntries)
    .set({ parentId: null, status: "draft" })
    .where(
      and(
        gte(scheduleEntries.day, input.startDate),
        lte(scheduleEntries.day, input.endDate),
      )
    )
    .returning({ id: scheduleEntries.id })

  return { success: true, clearedCount: result.length }
}
```

Critical implementation notes:
- BOTH actions call `requireAuthorizedParent()` as the very first statement after the `"use server"` boundary (line 1 of the file). This is the auth gate from existing line 16-23 — do not reimplement.
- `clearCell` mirrors `toggleCell` shape (lines 25-39) but sets `parentId: null` instead of a new ParentId. The `status: "draft"` write is intentional — clearing a previously-published cell flips it back to draft so the next publish runs the GCal cleanup orphan path.
- `clearRange` mirrors `extendSchedule` validation pattern (lines 113-140) but does an UPDATE instead of an INSERT. No `eq(scheduleEntries.status, ...)` filter — clearing must work on draft AND published rows.
- The 730-day cap exactly matches `extendSchedule`'s cap (line 128) for consistency.
- All Finnish error strings are exact — they are surfaced to the UI verbatim.

## Tech Debt (No Blockers)

### Phase 4: Google Calendar Sync

**FINDING-01: Publish/sync split across client round-trips**

`publishSchedule()` (lines 35-58 of `actions/schedule.ts`) and `syncCalendars()` (lines 60-77) are two separate Server Actions. `publish-button.tsx` calls them sequentially from the client: first publish, then — on success — sync. On the happy path this works correctly. But if the client loses network connectivity between the two calls, the schedule is marked `published` in the DB without any GCal events being created or cleaned up. There is no server-side retry, no job queue, and no recovery path. The next publish of the same entries will correctly create events (GCAL-03 idempotency handles this), but there's no signal to the user that sync was skipped.

This is an intentional best-effort design (sync failures shouldn't block publish), but the client-side split goes one step further than necessary. A single server-side `publishDraft` function that calls sync inside a try/catch would achieve the same failure isolation while eliminating the network-disconnect gap.

**Affected:** DRFT-02, GCAL-01, GCAL-02

---

### Phase 2: Schedule Table UI

**FINDING-02: Notes stored on first child's scheduleEntries row**

Shared day notes are stored on the `notes` column of the first child's `scheduleEntries` row for that day. The `schedules` table (which conceptually represents a "day in a schedule") exists in the schema but its `notes` column is unused — notes go into the first child's custody row instead. This works correctly for 2+ children but is a schema coupling: the `schedules` table is never queried for display data.

**Affected:** SCHED-05

---

### Configuration / Deployment

**FINDING-03: Placeholder emails in config.ts**

Both parents currently use `jarnoan@gmail.com` in `src/config/app.ts`. Comments in the file document this as a placeholder. The `buildGCalClient` function looks up OAuth tokens by email, so in production with two separate Google accounts, the mother's sync will use the wrong token. Requires manual update before deploying to a two-parent household.

**Affected:** GCAL-01, GCAL-04 (config change required, not code change)

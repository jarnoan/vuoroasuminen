<objective>
Switch the token-row write in the OAuth callback from the admin Drizzle connection (service_role, bypasses RLS) to the already-authenticated Supabase server client (session-scoped, triggers RLS policy evaluation). This makes the per-user RLS policy added in plan 03 (`(auth.jwt() ->> 'email') = email`) actually enforce — the callback can only write the signed-in user's own token row.

Purpose: Implements D-06 from CONTEXT.md. Without this change, the callback path would bypass RLS even after policies exist (because admin Drizzle uses service_role), making the per-user policy effectively cosmetic for token writes. The `supabase` variable returned by `createServerClient` is already in scope at the upsert location and carries the new session JWT after `exchangeCodeForSession` succeeds.

Output:
- `src/app/auth/callback/route.ts` upsert block uses `supabase.from('user_google_tokens').upsert(...)` instead of `db.insert(userGoogleTokens)...`
- Column names match the raw DB schema (`refresh_token`, `updated_at`), not the Drizzle camelCase aliases (`refreshToken`, `updatedAt`)
- Unused `db` and `userGoogleTokens` imports are removed
- Error handling preserves the redirect to `/auth/error` and the `[auth/callback]` log prefix
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| OAuth callback (server) → Supabase PostgREST | Authenticated session JWT crosses here; RLS policy on `user_google_tokens` enforces `(auth.jwt() ->> 'email') = email` |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-05 | Tampering | Callback writes a refresh token row for an arbitrary email value (e.g., a forged `userEmail`) | mitigate | RLS INSERT/UPDATE policy with `WITH CHECK ((auth.jwt() ->> 'email') = email)` added in plan 03 — Postgres rejects writes where the payload `email` ≠ JWT email claim. This plan removes the service_role bypass that previously made the policy moot. |
| T-09-06 | Information Disclosure | Refresh token logged in error output | mitigate | The replacement only logs `upsertError` (a PostgrestError) and `userEmail` — `providerRefreshToken` is never logged. Existing convention preserved. |
| T-09-07 | Denial of Service | PostgREST upsert error (e.g., RLS policy not yet present, or wrong column name) leaves user without a token row | accept | Failure redirects to `/auth/error`, which is the documented SAUTH-06 behavior. User can retry sign-in. Plan 03 must be applied before deployment to avoid spurious failures. |
| T-09-08 | Elevation of Privilege | A user manipulates `data.session.user.email` to write another user's row | mitigate | `userEmail` comes from the just-exchanged session — Supabase signs the JWT server-side; it cannot be tampered with by the browser. RLS policy in plan 03 additionally enforces the match. |
</threat_model>

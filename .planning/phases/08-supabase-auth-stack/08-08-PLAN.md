<objective>
**[BLOCKING — HUMAN GATE]** This plan is the formal Phase 8 → Phase 9 gate from ROADMAP.md. It runs no code itself; instead, it pauses the workflow and presents a checklist of 5 end-to-end behaviors that the human must verify in a real browser against the running app. Phase 9 (Row Level Security) MUST NOT begin until every box is checked.

The 5 criteria, copied verbatim from ROADMAP.md §Phase 8 Success Criteria, also satisfy every requirement ID for this phase: SAUTH-01..07, GCAL-01, GCAL-02.

Why a human gate (not automation): SAUTH-01 (Google consent screen), SAUTH-04 (browser redirect behavior), SAUTH-07 (visual banner state), and GCAL-01 (calendar event appearance in Google Calendar) involve external systems (Google OAuth, Google Calendar UI) that cannot be reliably scripted in a Vitest/Playwright run inside this project's current setup. Phase 9 RLS is a one-way door — once domain-table policies are turned on, debugging an undiscovered Phase 8 regression becomes harder. The gate protects against that.

Output: Confirmation that all 5 criteria pass, or a list of failures that block Phase 9. Failures route to gap closure (`/gsd-plan-phase --gaps`).
</objective>

**PRE-FLIGHT (do these before running the 5 tests):**

a. Confirm operational setup is complete (see `<interfaces>` block above — Supabase Dashboard, Google Cloud Console, .env.local).

b. Drop any existing `user_google_tokens` rows so you start from a clean slate (this lets you observe the row appearing on first sign-in):
   ```bash
   node -e "const {Pool}=require('pg');const p=new Pool({connectionString:process.env.DATABASE_URL,ssl:{rejectUnauthorized:false}});p.query('DELETE FROM user_google_tokens').then(r=>{console.log('Deleted',r.rowCount,'token rows');return p.end();}).catch(e=>{console.error(e.message);process.exit(1);});"
   ```

c. Clear Auth.js cookies in your browser so they don't interfere (DevTools → Application → Cookies → delete any cookie starting with `next-auth.`).

d. Start the dev server:
   ```bash
   npm run dev
   ```



**TEST 1 — SAUTH-01: PKCE Google sign-in lands on /dashboard**

1. Open `http://localhost:3000/` in a fresh browser session (or incognito).
2. Confirm you see the home page with the heading "Vuoroasuminen", subheading "Yhteinen vuoroasumisaikataulu vanhemmille", and the button "Kirjaudu sisään Googlella".
3. Click the button.
4. EXPECTED: Browser redirects to Google's consent screen showing your app name and the requested scopes (must include `Google Calendar`). Pick the calendar owner's account (whoever you set as `APP_CALENDAR_OWNER_EMAIL`, or one of the parent emails if running in legacy mode).
5. Approve the consent screen.
6. EXPECTED: Browser redirects to `https://<supabase-ref>.supabase.co/auth/v1/callback`, then to `http://localhost:3000/auth/callback?code=...`, then to `http://localhost:3000/dashboard`. The final URL bar shows `/dashboard`.
7. EXPECTED: The dashboard renders (header with your avatar + name + "Kirjaudu ulos" button, schedule grid below).

PASS iff the final URL is `/dashboard` and the dashboard content renders. FAIL if you land on `/auth/error` (means provider_refresh_token was null — see SAUTH-06 test below for the deliberate failure path).



**TEST 2 — SAUTH-02: Session persists across page refresh**

1. After completing TEST 1, on the `/dashboard` page, hit the browser refresh button (Cmd+R / F5).
2. EXPECTED: The page reloads and STAYS on `/dashboard` showing your authenticated state — same avatar, same name, same schedule.
3. EXPECTED: You are NOT redirected to `/`.
4. Open DevTools → Application → Cookies for `localhost:3000`. EXPECTED: there is at least one cookie whose name starts with `sb-` (Supabase session cookie).

PASS iff the dashboard renders without a redirect to home.



**TEST 3 — SAUTH-06 + Database row written**

1. After TEST 1, query the database to confirm a `user_google_tokens` row was written:
   ```bash
   node -e "const {Pool}=require('pg');const p=new Pool({connectionString:process.env.DATABASE_URL,ssl:{rejectUnauthorized:false}});p.query('SELECT email, length(refresh_token) AS token_len, updated_at FROM user_google_tokens').then(r=>{console.log(JSON.stringify(r.rows,null,2));return p.end();}).catch(e=>{console.error(e.message);process.exit(1);});"
   ```
2. EXPECTED: One row, with `email` matching the Google account you signed in with, `token_len` greater than 0 (typical Google refresh tokens are 100+ characters), `updated_at` within the last few minutes.

PASS iff the query returns exactly the expected row with non-null refresh_token. FAIL (and route to gap closure) if `refresh_token` is null or the row is missing — that means SAUTH-06's error redirect should have fired but didn't, or the upsert silently failed.



**TEST 4 — GCAL-01 + GCAL-02: Publish triggers sync via ownerEmail**

1. Still on `/dashboard`, click some schedule cells to assign at least one cell to each parent for the next few days (creates draft entries).
2. Click the "Julkaise" / publish button.
3. EXPECTED: The publish action succeeds (button transitions; no error toast).
4. Open the configured Google Calendars (both `PARENT_FATHER_CALENDAR_ID` and `PARENT_MOTHER_CALENDAR_ID`). EXPECTED: All-day events appear on the days you assigned, titled with the child name and the parent name (e.g. `"Taimi @ Isä"`).
5. CRITICAL CHECK: Sign out (TEST 6 below), sign in as the OTHER parent (the one whose email is NOT in `APP_CALENDAR_OWNER_EMAIL`), and press publish again on a fresh draft. EXPECTED: GCal sync still works — events still appear on both calendars — because the configured owner's token is used regardless of who pressed publish (D-01 / GCAL-01).

PASS iff all-day events appear on both calendars after publish, AND publish works regardless of which parent triggered it. FAIL if `Calendar authentication failed for X` shows in server logs (means owner email lookup is broken).



**TEST 5 — SAUTH-07: Dashboard banner appears when owner has no token row**

1. Sign out via the header's "Kirjaudu ulos" button (this also tests SAUTH-03).
2. EXPECTED: Browser redirects to `/`.
3. Drop the owner's token row again (simulating a fresh deploy or token revocation):
   ```bash
   node -e "const {Pool}=require('pg');const p=new Pool({connectionString:process.env.DATABASE_URL,ssl:{rejectUnauthorized:false}});p.query('DELETE FROM user_google_tokens').then(r=>{console.log('Deleted',r.rowCount,'token rows');return p.end();}).catch(e=>{console.error(e.message);process.exit(1);});"
   ```
4. Sign in as the OTHER parent (NOT the configured owner — so the owner's row stays missing). For local single-owner-mode test, you can sign in as the owner but immediately delete just their row, then refresh dashboard:
   - Easier alternative: temporarily set `APP_CALENDAR_OWNER_EMAIL` in `.env.local` to a Google account that has NEVER signed in to the app. Restart `npm run dev`. Sign in as one of the parent emails.
5. Land on `/dashboard`. EXPECTED: A banner appears between the header and the schedule toolbar. Banner text: `"Kalenterin omistaja ei ole kirjautunut — kalenterisynkronointi ei toimi."` Followed by a link "Kirjaudu sisään".
6. Click the X button on the right of the banner. EXPECTED: Banner disappears.
7. Hit browser refresh (Cmd+R). EXPECTED: Banner reappears (per-session dismiss; D-07 — no localStorage).
8. Click the "Kirjaudu sisään" link inside the banner. EXPECTED: Browser redirects to Google consent screen (same as TEST 1).
9. Sign in as the configured owner. EXPECTED: After the callback, dashboard re-renders WITHOUT the banner (because the owner's row now exists).

PASS iff the banner appears, dismisses, re-appears on refresh, and disappears after the owner signs in.

**(Optional bonus check — also satisfies SAUTH-03 explicitly)**: confirm the sign-out flow works: click header's "Kirjaudu ulos" → page navigates to `/` → header is gone → sign-in button is back.

**(Optional bonus check — SAUTH-04)**: while signed out, type `http://localhost:3000/dashboard` directly into the URL bar. EXPECTED: middleware redirects you to `/`.

**(Optional bonus check — SAUTH-05)**: in DevTools → Network, filter for the `signInWithOAuth` redirect URL. EXPECTED: the URL contains `access_type=offline&prompt=consent` query params.

```typescript
import { NextResponse } from "next/server"
import type { NextRequest } from "next/server"
import { createSupabaseMiddlewareClient } from "@/lib/supabase/middleware"

export async function middleware(request: NextRequest) {
  // CRITICAL (D-10): create the response and Supabase client INSIDE the handler.
  // Module-scope clients leak sessions between users on Vercel warm instances.
  const response = NextResponse.next()
  const supabase = createSupabaseMiddlewareClient(request, response)

  // CRITICAL (D-09): getUser() validates the JWT server-side. getSession() trusts
  // a spoofable cookie and MUST NOT be used for route protection.
  const {
    data: { user },
  } = await supabase.auth.getUser()

  const pathname = request.nextUrl.pathname
  const isOnHome = pathname === "/"
  const isOnAuthRoute = pathname.startsWith("/auth/")

  if (!user && !isOnHome && !isOnAuthRoute) {
    return NextResponse.redirect(new URL("/", request.url))
  }

  return response
}

export const config = {
  // Pitfall 4: exclude api/auth (NOT just api) so the Auth.js [...nextauth] route
  // handler at /api/auth/* keeps working while Auth.js coexists in Phase 8.
  matcher: ["/((?!api/auth|_next/static|_next/image|favicon.ico).*)"],
}
```

Why these exact choices (do NOT change them):
- Helper import (`createSupabaseMiddlewareClient`) instead of inlining `createServerClient` — keeps the cookie wiring in one place (Plan 02), reduces drift risk.
- `NextResponse.next()` first, then build the supabase client around `response` — required so the supabase client's `setAll` callback writes to a response object that exists.
- `await supabase.auth.getUser()` — destructure `data: { user }` only; we don't read `error` because the unauthenticated case (user === null) is the same code path.
- `/auth/` prefix check (not exact match on `/auth/callback` or `/auth/error`) — covers both the callback and error pages without listing each.
- Return `response` (the one passed to the supabase client), NOT a new `NextResponse.next()` — otherwise refreshed session cookies set by Supabase get dropped (variant of Pitfall 3).
- `matcher` excludes `api/auth` (not all `api/*`) — Pitfall 4 explicitly covers this. The new app does not have non-auth `/api` routes that need middleware right now, but excluding only `api/auth` is the safer / more flexible default and matches the existing matcher's spirit.

Do NOT add: a `getSession()` fallback (forbidden — D-09), any module-scope variables, an else branch that returns `NextResponse.next()` separately (would lose cookies), or a try/catch swallowing `getUser()` errors (let them surface in dev).

```typescript
import { NextResponse } from "next/server"
import type { NextRequest } from "next/server"
import { createServerClient } from "@supabase/ssr"
import { db } from "@/db"
import { userGoogleTokens } from "@/db/schema/tokens"

export async function GET(request: NextRequest) {
  const { searchParams } = new URL(request.url)
  const code = searchParams.get("code")

  if (!code) {
    return NextResponse.redirect(new URL("/auth/error", request.url))
  }

  // CRITICAL (Pitfall 3): build the response BEFORE creating the Supabase client
  // so the cookie setAll callback has a response object to write session cookies to.
  // If the redirect is constructed after exchangeCodeForSession, the session cookies
  // are silently dropped and the browser remains unauthenticated.
  const response = NextResponse.redirect(new URL("/dashboard", request.url))

  const supabase = createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
    {
      cookies: {
        getAll() {
          return request.cookies.getAll()
        },
        setAll(cookiesToSet) {
          cookiesToSet.forEach(({ name, value, options }) => {
            response.cookies.set(name, value, options)
          })
        },
      },
    },
  )

  const { data, error } = await supabase.auth.exchangeCodeForSession(code)

  if (error || !data.session) {
    return NextResponse.redirect(new URL("/auth/error", request.url))
  }

  // SAUTH-06: provider_refresh_token is only available HERE — not in subsequent
  // getSession() calls. If Google did not return one (e.g. user had a prior
  // consent grant without prompt:consent), redirect to the error page so the
  // user can re-grant with the correct OAuth params.
  const providerRefreshToken = data.session.provider_refresh_token
  const userEmail = data.session.user.email

  if (!providerRefreshToken || !userEmail) {
    return NextResponse.redirect(new URL("/auth/error", request.url))
  }

  // D-11: write via the admin Drizzle connection (DATABASE_URL bypasses RLS).
  // onConflictDoUpdate handles re-sign-ins as upserts on the email PK,
  // avoiding race conditions if the user signs in twice in quick succession.
  await db
    .insert(userGoogleTokens)
    .values({
      email: userEmail,
      refreshToken: providerRefreshToken,
      updatedAt: new Date(),
    })
    .onConflictDoUpdate({
      target: userGoogleTokens.email,
      set: {
        refreshToken: providerRefreshToken,
        updatedAt: new Date(),
      },
    })

  return response
}
```

Why these exact choices (do NOT change them):
- Inline `createServerClient` from `@supabase/ssr` instead of the Plan 02 server helper — the helper uses `next/headers` `cookies()` which is a different cookie-store API. Route handlers in this PKCE flow MUST wire cookies to a specific `request`/`response` pair so cookies land on the redirect response (Pitfall 3). The middleware-style wiring is the only correct shape here.
- `NextResponse.redirect(new URL("/dashboard", request.url))` BEFORE the supabase client — order matters per Pitfall 3.
- Three separate redirect-to-error checks: (a) no `code`, (b) `error || !data.session`, (c) `!providerRefreshToken || !userEmail`. Combining them risks treating a valid-session-without-refresh-token case as a hard error and would skip the explicit SAUTH-06 path that takes the user to the error page where they can re-grant.
- `target: userGoogleTokens.email` in `onConflictDoUpdate` — uses the email PK as the conflict key. The `set` block updates `refreshToken` and `updatedAt`; do NOT set `email` again (it's the conflict target).
- `new Date()` in two places (values + set) — required by `{ mode: "date" }` from Plan 01's schema. Drizzle does not auto-fill `defaultNow()` on conflicting upserts.

Do NOT: try to read `provider_token` (we never use it), wrap the upsert in a try/catch (let real DB errors surface as 500), call `revalidatePath` (the redirect handles it), use `cookies()` from `next/headers` (wrong API for this context).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → Supabase Auth Server | OAuth state + PKCE code verifier travel via cookies; Supabase SSR manages PKCE verifier integrity. |
| Supabase Auth → /auth/callback | The `code` param is treated as untrusted input; only `exchangeCodeForSession` validates it. |
| /auth/callback → user_google_tokens | Server writes `provider_refresh_token` keyed on the email returned by `exchangeCodeForSession`. The email is JWT-attested by Google → Supabase. |
| Browser cookie → middleware | Session cookies are validated server-side via `getUser()` (D-09); spoofed cookies fail JWT verification. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-04-01 | Spoofing | Cookie-based middleware identity | mitigate | D-09 lock: middleware uses `supabase.auth.getUser()` which contacts the Supabase Auth server to verify the JWT signature and expiry. Spoofed cookies cannot impersonate a user because the JWT signature would not validate. Verified via grep `! getSession` in Task 1. |
| T-08-04-02 | Tampering | OAuth code injection in /auth/callback | mitigate | The `code` param is fed only to `supabase.auth.exchangeCodeForSession(code)` which is the official Supabase verification entry point — it validates the code against Supabase's own state and returns an error for tampered/unknown codes. We branch on `error || !data.session` and redirect to `/auth/error` rather than leaking the error or proceeding. |
| T-08-04-03 | Information Disclosure | provider_refresh_token persisted in clear | accept | Same disposition as T-08-01-01 (Plan 01). Stored in DATABASE_URL-protected Postgres; RLS in Phase 9 restricts row visibility to the row owner. At-rest encryption is out of v1.2 scope. |

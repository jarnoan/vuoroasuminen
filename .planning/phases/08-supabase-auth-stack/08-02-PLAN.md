Create new file `src/lib/supabase/server.ts` with the EXACT content below. This is the canonical server helper — every Server Component / Server Action / Route Handler in Plans 04, 05, and 07 will import from here.

```typescript
import { createServerClient } from "@supabase/ssr"
import { cookies } from "next/headers"

export async function createSupabaseServerClient() {
  const cookieStore = await cookies()
  return createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
    {
      cookies: {
        getAll() {
          return cookieStore.getAll()
        },
        setAll(cookiesToSet) {
          try {
            cookiesToSet.forEach(({ name, value, options }) => {
              cookieStore.set(name, value, options)
            })
          } catch {
            // Server Components cannot set cookies — ignore. Middleware refreshes
            // the session instead. This try/catch is the standard @supabase/ssr
            // pattern for Server Component contexts.
          }
        },
      },
    }
  )
}
```

Why these exact choices:
- `await cookies()` — Next.js 15/16 made cookies async; calling without await causes runtime warnings.
- `getAll`/`setAll` callbacks (NOT the deprecated single `get`/`set`/`remove` shape) — required by `@supabase/ssr` 0.10.x for chunked cookie support.
- `try/catch` around `cookieStore.set` — Server Components throw when called from a render context that cannot mutate cookies; the official Supabase SSR Next.js pattern catches and ignores because middleware refreshes the cookies on the next request anyway.
- Function is async because `cookies()` is async — callers MUST `await createSupabaseServerClient()`.
- Env vars read inside the function (not at module scope) — keeps the function pure per request and avoids stale env caches in dev hot-reload.

Do NOT export any other helpers from this file (no `getServerUser`, no convenience wrappers). Plans that need the user just call `(await createSupabaseServerClient()).auth.getUser()` directly.

Create new file `src/lib/supabase/middleware.ts` with the EXACT content below. The middleware in Plan 04 will call this factory inside the request handler — never at top level.

```typescript
import { createServerClient } from "@supabase/ssr"
import type { NextRequest, NextResponse } from "next/server"

/**
 * Per-request Supabase client for middleware contexts.
 *
 * CRITICAL (D-10): Always call this INSIDE the middleware function body —
 * never assign the result to a module-scope variable. Vercel warm instances
 * share module scope across requests; a cached client would leak one user's
 * session to the next request.
 */
export function createSupabaseMiddlewareClient(
  request: NextRequest,
  response: NextResponse,
) {
  return createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
    {
      cookies: {
        getAll() {
          return request.cookies.getAll()
        },
        setAll(cookiesToSet) {
          cookiesToSet.forEach(({ name, value, options }) => {
            response.cookies.set(name, value, options)
          })
        },
      },
    },
  )
}
```

Why these exact choices:
- Sync function (no `await`) — `request.cookies.getAll()` is synchronous; no `next/headers` involved.
- `request` is the source-of-truth for incoming cookies; `response` is the destination for refreshed session cookies.
- `setAll` is required by `@supabase/ssr` 0.10.x — Supabase chunks long cookies and writes them in batches.
- Type imports from `next/server` (not `next`) — these are the Edge runtime types that work in middleware.
- The doc comment explicitly cites D-10 to prevent any future contributor from caching the client at module scope.

Do NOT add `await`, do NOT import `next/headers`, do NOT memoize, do NOT add a `getUser()` convenience wrapper.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser cookie → server | Both helpers parse session cookies received from the browser. Cookies could be forged or tampered with. |
| `process.env` → Supabase server | Helpers send the anon key to Supabase; the anon key is public-safe (RLS enforces actual access). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-02-01 | Spoofing | Cookie-based session validation | mitigate | These helpers expose `auth.getUser()` (not `getSession()`) per D-09 — every consumer in Plans 04/05/07 contacts the Supabase Auth server to verify the JWT, so a spoofed cookie cannot impersonate a real user. The helpers themselves do not auto-call any auth method; consumers are responsible for using `getUser()`. |
| T-08-02-02 | Information Disclosure | Module-scope session leak (Vercel warm) | mitigate | `createSupabaseMiddlewareClient` is a pure factory with no module-scope state (D-10). The doc comment explicitly forbids memoization. The matching middleware in Plan 04 will call the factory inside the handler. |
| T-08-02-03 | Tampering | Anon key exposure | accept | `NEXT_PUBLIC_SUPABASE_ANON_KEY` is by design public — Supabase RLS (Phase 9) enforces row-level access using the JWT, not the anon key. Existing Realtime client at `src/lib/supabase/client.ts` already uses the same env var with no additional mitigation. |
| T-08-02-04 | Repudiation | Cookie write failures in Server Components | accept | The try/catch around `cookieStore.set` in `server.ts` swallows writes that fail in Server Component render contexts. This is the official Supabase SSR pattern; the next middleware request refreshes the cookie. No user data is lost — only the session refresh is deferred by one request. |
</threat_model>
